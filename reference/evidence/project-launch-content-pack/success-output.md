## 4. 传播核心

### 一句话定位

**Workflow-to-Skill 不是再造一个工作流引擎，而是把目标、方法、权限边界、失败恢复和成功证据写进一个可复用的 `SKILL.md`，让 Agent Harness 调用已有工具完成工作。**

### 受众问题

熟悉 Dify、n8n 或 ComfyUI 的开发者，通常已经拥有能够真正执行任务的图、API、CLI 或外部系统。新的问题是：

- 如何让 Agent 理解这些能力应当在什么目标下使用？
- 哪些参数可以自行判断，哪些必须交给人审阅？
- 超时、部分成功或状态不确定时，应该如何停止和恢复？
- 什么证据才足以宣称任务完成？
- 如何把这套方法交给下一次 Harness 会话复用？

### 项目机制

```text
目标 + 输入 + 真实能力
→ 推荐方法与决策
→ 失败与恢复行为
→ 可验证结果
```

最终形成普通、可读的 `SKILL.md`。Harness 负责发现 Skill、运行 Agent 和调用工具；外部系统继续拥有实际执行与持久状态。

### 具体差异

它主要增加的是一层**可读的工作流语义与边界**，不是另一层执行基础设施：

- 不要求先画 DAG；
- 不复制外部工作流图；
- 不发明通用工具或权限协议；
- 不把“提交成功”宣传成“任务完成”；
- 不具备的能力必须明确报告为集成缺口。

### 有用的下一步

进入仓库后，建议先检查：

1. `README.zh-CN.md` 中的核心思想与边界；
2. `workflow-to-skill/SKILL.md` 的创作流程；
3. 目标 Harness 是否真的具备所需工具、权限和验证信号；
4. 再选择一个低风险、可验证的小工作流进行试用。

## 5. 定位与主张边界

### 可以说

- “一种把工作流方法写进 Agent Skill 的方式。”
- “复用已有 CLI、MCP、HTTP、API 或外部工作流。”
- “强调审阅、权限、失败恢复和成功证据。”
- “README 报告了一个在 DSH 中完成的端到端案例。”
- “可移植的是方法；具体工具、权限和生命周期仍绑定于 Harness。”

### 不应说

- “取代 Dify、n8n 或 ComfyUI。”
- “兼容所有 Agent 或所有 Harness。”
- “无需任何集成即可跨平台运行。”
- “已经验证所有外部工具和工作流系统。”
- “所有任务都比 DAG 更适合用 Skill。”
- “生产级”“行业第一”“零风险”“开箱即用”等来源未支持的宣传语。
- 把 README 报告的测试或案例描述为本次已经重新运行并验证。

## 6.2 正文草稿

如果你已经在用 Dify、n8n、ComfyUI，或者给 Agent Harness 接过 CLI、MCP、HTTP、API，可能会遇到另一个问题：

**工具已经有了，怎样把“什么时候用、怎么判断、失败怎么办、凭什么算完成”交给 Agent 复用？**

Workflow-to-Skill 提供的是一种很克制的做法：把一个可复用工作流写成普通的 `SKILL.md`。

它不是新的 DAG、DSL 或执行引擎。Skill 负责说明：

- 目标、输入和适用范围  
- 需要哪些真实能力  
- 推荐方法与决策边界  
- 什么必须人工审阅  
- 超时、部分成功和不确定结果怎么处理  
- 哪些证据才能证明任务完成  

真正的工作仍由 Harness 和已有系统执行。Dify、n8n、ComfyUI、CLI 或 API 不需要被“搬进”Skill；如果目标 Harness 没有对应能力，就应该报告集成缺口，而不是虚构一个工具。

我觉得这里最值得讨论的一条原则是：

```text
工具调用被接受
≠ 请求已提交
≠ 外部工作成功
≠ 结果已经验证
```

README 还报告了一个 DSH 端到端案例：先生成领域 Skill，再由全新会话发现并明确调用。不过，仓库也主动限定了证据范围——这不能直接证明未经测试的 Dify、n8n、ComfyUI 或任意跨 Harness 行为。

如果你正在搭 Agent 工具链，可以先去读 `README.zh-CN.md` 和 `workflow-to-skill/SKILL.md`，再挑一个低风险、结果可核验的小任务试试。重点不只是“能不能跑”，而是看看它有没有把权限、失败和成功证据写清楚。

## 7.1 标题建议

1. **Agent 工作流一定要画成 DAG 吗？Workflow-to-Skill 提供了另一种思路**
2. **如何把已有 Dify、n8n 或 CLI 能力变成可复用的 Agent Skill？**
3. **为什么 Workflow-to-Skill 不打算再造一个工作流运行时？**
4. **一个 `SKILL.md` 能承载工作流吗？关键可能不是编排，而是边界与证据**
5. **从“工具能调用”到“结果已验证”，Agent 工作流中间还缺什么？**

## 7.2 长文草稿

熟悉 Dify、n8n、ComfyUI 的开发者，通常不会缺少“执行能力”：图形化工作流、API、CLI、MCP 工具或者某个外部任务系统，都可以真正完成工作。

但把这些能力接给 Agent 之后，会出现一组新的问题：

- Agent 应当在什么目标和范围内调用它们？
- 哪些参数可以安全推断，哪些选择必须让人审阅？
- 工具超时、返回部分结果或状态不确定时怎么办？
- 一次调用被接受，是否足以宣称任务已经完成？
- 如何让下一次 Harness 会话复用同样的方法，而不是重新解释一遍？

Workflow-to-Skill 试图解决的，正是这层“方法与边界”的复用问题。

## 一、工作流不一定是一张图

这个仓库给出的核心表达是：

```text
目标 + 输入 + 真实能力
→ 推荐方法与决策
→ 失败与恢复行为
→ 可验证结果
```

最终产物是一个普通的 `SKILL.md`。它是 Agent 可以阅读的方法，不是 DAG、DSL、编译程序或新的运行时。

这种区分很重要。Workflow-to-Skill 不负责拥有执行器、工具注册表、队列、调度器或持久状态；Harness 负责加载 Skill、运行 Agent 并调用工具，CLI、MCP、HTTP、API，以及 Dify、n8n、ComfyUI 等已有系统继续承担真实执行。

因此，它更像是给既有能力补上一份“Agent 可执行、又可供人审阅的操作规范”，而不是用另一套系统替换现有工具。

## 二、一个工作流 Skill 需要写清什么？

根据仓库中的创作标准，一个生成的 Skill 至少需要覆盖五类信息。

第一是**目标与输入**：结果是什么，适用于哪些情况，排除什么，完成标准是什么，必需和可选输入如何验证。

第二是**真实能力**：需要什么语义能力；如果已经知道目标 Harness 的具体绑定，还要说明准确工具、参数、结果、权限、凭据名称和生命周期假设。缺失的绑定不能靠猜。

第三是**方法与权限**：推荐步骤是什么，数据如何传递，哪些低风险细节可以由 Agent 判断，哪些实质性选择必须经过审阅，遇到什么情况必须停止。

第四是**失败与恢复**：如何处理缺少依赖、错误、超时、取消、部分结果和不确定结果。重试也不是默认安全的，尤其是可能产生副作用的操作。

第五是**验证与输出**：什么外部状态、产物、来源、回执或业务检查能够证明完成，以及最终向用户展示什么。

这意味着，一个 Skill 的价值不只是“把步骤写下来”，而是把成功和失败都写成可检查的契约。

## 三、最值得保留的是“运行时真相”

仓库反复强调：

```text
工具调用被接受
≠ 请求已提交
≠ 外部工作成功
≠ 结果已经验证
```

这对 Agent 工具开发尤其重要。很多演示只展示工具调用已经发出，却没有确认外部任务是否进入终态，也没有取得可检查的产物或回执。

Workflow-to-Skill 的要求是：只有 Skill 声明的成功证据确实存在，才能报告成功。如果只能看到提交，就只能报告提交；如果结果无法确认，应如实标记为运行中、部分完成、失败、取消、未知或未验证。

对于有副作用的任务，审批也不能替代防重复机制。仓库要求在真实能力提供操作 ID、状态查询、幂等性或其他去重约定时，才据此核对和安全恢复。否则应该停止，而不是盲目重试。

## 四、它与 Dify、n8n、ComfyUI 是什么关系？

更准确的说法不是“替代”，而是“复用”。

如果你已有一个 n8n 同步流程、Dify 知识工作流或 ComfyUI 生成图，Skill 可以描述何时调用、输入如何检查、遇到失败如何处理、最终需要什么运行 ID、终态或输出产物作为证据。

但前提是目标 Harness 确实提供了调用这个外部系统所需的提交、查询、取消和结果接口。Workflow-to-Skill 本身不会凭空提供这些能力，也不会把外部工作流图复制进 Skill。

仓库还明确承认当前证据边界：README 报告了一个在 DeepSeek Harness 中完成的端到端案例，但这些材料不能证明未经测试的 Dify、n8n、ComfyUI、任意 CLI 或所有跨 Harness 行为。共享 Skill 语法，也不等于不同 Harness 拥有相同的运行行为。

## 五、什么场景值得试？

它比较适合那些需要 Agent 判断、人工审阅、失败恢复或结果解释的重复任务，例如有来源的研究简报、代码检查与验证、数据调查、文档比较，或调用已有外部工作流。

它并非适合所有问题。如果任务只是固定、确定性的转换，一个普通脚本可能更清楚；如果系统必须自己管理严格并发、持久队列、调度或长时间状态机，运行时仍应留在代码或已有系统中。

如果要试用，建议不要从高风险自动化开始。可以先选择一个只读、结果容易核验的小任务：

1. 阅读 `README.zh-CN.md`，确认项目边界；
2. 检查 `workflow-to-skill/SKILL.md` 的创作要求；
3. 列出目标 Harness 已有的真实工具和验证信号；
4. 生成一个领域 Skill；
5. 在全新会话中确认发现并明确调用；
6. 分别测试一个成功场景和一个安全的失败场景。

值得检查的不只是“能不能调用工具”，而是生成的 Skill 有没有诚实回答三个问题：**它被允许做什么，失败时怎样停止，什么证据才算完成。**

# 8. 总体视觉简报

## 视觉目标

让熟悉节点式工作流的开发者快速看懂：Workflow-to-Skill 增加的是**可读的方法与验证边界**，不是另一个执行引擎。

## 推荐视觉语言

- **风格**：技术文档感、代码编辑器感、克制，不使用夸张“革命性”视觉。
- **主色**：深蓝或炭黑底色，青蓝作为 Skill，绿色仅用于“证据已存在”，黄色用于“待审阅/未验证”。
- **核心符号**：
  - `SKILL.md` 文件卡；
  - Harness 作为调用中枢；
  - CLI/MCP/API/外部工作流作为已有能力；
  - 回执、来源、终态作为验证信号。
- **避免**：
  - 把 Dify、n8n、ComfyUI 画成被替代或淘汰；
  - “全平台兼容”“一次配置永久运行”等无依据标语；
  - 将 README 报告的 DSH 案例视觉化为普遍性能结论；
  - 使用未经核实的产品 Logo 或官方合作、背书暗示。

## 核心构图

```text
         SKILL.md
目标 / 方法 / 权限 / 恢复 / 证据
              ↓
      Harness + Agent
              ↓
CLI / MCP / HTTP / API / 外部工作流
              ↓
```
